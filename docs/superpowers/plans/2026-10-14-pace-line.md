# Pace Line Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After every pull, report how far ahead of / behind a benchmark (own best timed run, else the timer) the key was, and what each pull gained or lost.

**Architecture:** A pure module `analysis/pace.py` turns finished reports into pace points (like `verdict.py`: no log access, hostile-input safe). `history/benchmark.py` picks the benchmark from the local history store and attaches `report["pace"]`. The CLI, Watch Live, the desktop app and History call it; `render_html` falls back to a timer-only pace for any report without one, and draws a Pace section plus a Pace column in the Pulls table.

**Tech Stack:** Python 3 stdlib only, pytest, the report's inline JS (tested through node via `tests/test_report_escaping._run`).

**Spec:** `docs/superpowers/specs/2026-10-14-pace-line-design.md`

## Global Constraints

- Stdlib only; every change has tests (repo convention).
- Progress = 0.5 x forces fraction + 0.5 x bosses killed / total bosses; an unknown half is dropped and the other counts fully; neither -> no pace.
- Game time = seconds since key start + deaths so far x `death_cost.per_death_s`.
- Benchmark order: same dungeon, timed, not this run -> same level -> nearest level (ties: higher first) -> fastest duration -> else timer.
- Timer budget at progress p = par x p; +2 / +3 budgets = 0.8 / 0.6 x par x p.
- `delta_s` positive = behind. `change_s` = this point's delta - previous point's delta (first point: its own delta).
- Captions, verbatim shapes: "vs your best +17 (26:40, Sep 28)", "vs your best +16 (no timed +17 yet)", "vs the timer (no timed run of this dungeon yet)".
- Every pace step is best-effort: a failure never fails analysis, rendering or ingest; the report simply has no pace (render falls back to timer).
- Nothing is tagged or deployed; the user tests first. The site's account-based lookup is a separate plan in `postmortem-site`.

## Review Focus

1. Re-analysing a run that is already in history must not use itself as the benchmark (same zone + `start_ts`) -> Task 2 test.
2. The fastest candidate is an old stored report with no forces/encounters data -> that candidate yields no points; fall back to the next candidate, then the timer -> Task 2 test.
3. A run analysed without dungeon data (`forces.required` null, CLI default) -> bosses-only progress, not "no pace" -> Task 1 test.
4. An unfinished key (abandoned at 60%) -> points only for pulls done; total bosses from the own-best benchmark, else forces-only -> Task 1 test.
5. Hostile report values (strings, NaN, bools, missing `t_end`, unsorted forces timeline) -> no exception, bad points skipped -> Task 1 test.

### Task 1: Pace calculation (`analysis/pace.py`)

**Files:**
- Create: `src/postmortem/analysis/pace.py`
- Test: `tests/test_pace.py`

**Interfaces:**
- Produces:
  - `PACE_VERSION = 1`
  - `progress_points(report: dict, total_bosses: Optional[int] = None) -> list[dict]` -- one dict per pull with a numeric `t_end`, in pull order: `{"pull", "t_end", "progress", "game_s"}`. `total_bosses=None` -> distinct killed bosses if `run.completed`, else bosses half dropped.
  - `boss_count(report: dict) -> Optional[int]` -- distinct `encounter_id` (else `name`) with `kill: true`, only when `run.completed` is true.
  - `build_pace(report: dict, benchmark: Optional[dict] = None, benchmark_info: Optional[dict] = None) -> Optional[dict]` -- `benchmark` is the benchmark's full report (None -> timer). `benchmark_info` is `{"level", "duration_s", "date", "same_level"}` copied into the output. Returns the spec's `report["pace"]` shape or None.

Reading the report: pull end = `pulls[i].t_end` (seconds from key start). Forces done at time t = last `forces.timeline` entry with `t <= t_end` (sort by `t` first; field `forces` is cumulative), divided by `forces.required`, capped at 1. A boss is killed by t when `encounter.kill` and `encounter.t + encounter.duration_s <= t_end`. Deaths so far = `deaths` with numeric `t <= t_end`. Timer par = `timer.par_ms / 1000`. Own-best curve = the benchmark's `progress_points` plus `(0, 0)` and `(1, benchmark run.duration_ms / 1000)`, progress made non-decreasing (running max), then linear interpolation. Reuse `verdict._num/_int/_dict/_list` for every read.

### Task 2: Benchmark selection and attach (`history/benchmark.py`)

**Files:**
- Create: `src/postmortem/history/benchmark.py`
- Test: `tests/test_pace_benchmark.py`

**Interfaces:**
- Consumes: `pace.build_pace`, `pace.boss_count`; `history.store.Store.query_runs_with_ids() -> list[tuple[int, dict]]` (index rows: `zone, level, timed, duration_ms, start_ts, date`) and `Store.get_report(run_id) -> Optional[dict]`.
- Produces:
  - `rank_candidates(report: dict, rows: list[tuple[int, dict]]) -> list[tuple[int, dict]]` -- filtered and ordered best-first per the Global Constraints order.
  - `attach_pace(report: dict, db_path: Optional[str | Path]) -> dict` -- sets `report["pace"]` (own best when one yields points, else timer) and returns the report. Never raises; `db_path` None or missing DB -> timer pace.

Matching: same dungeon = same `run.zone` string; "this run" = same zone and `abs(start_ts - run.start_ts) < 1`. For each ranked candidate, load its report and use it if `progress_points` of it is non-empty; else try the next (Review Focus 2). `benchmark_info`: `level`, `duration_s = duration_ms / 1000`, `date` = first 10 chars of the row's `date`, `same_level = level == run.keystone_level`. For an unfinished run pass `boss_count(benchmark)` as `total_bosses`.

  - `test_nearest_level_prefers_higher_on_a_tie`: run +17, rows +16 and +18 -> +18 first, then +16.
